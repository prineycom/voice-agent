# Epic 8 — Phase 0 Feasibility Spike: Audio2Face-3D on the Desktop

Date: 2026-07-03. Goal: determine whether/how A2F-3D can run on the Desktop (RTX 4070 12GB,
Windows 11), pick a deployment path, and validate the epic's assumptions. See ADR-0012, Epic #33.

## Desktop baseline (measured)

- **GPU:** RTX 4070, 12282 MiB total. **7180 MiB used / 4833 MiB free** with STT+TTS running.
- **Driver:** 596.49 (satisfies A2F's R570+ / CUDA 12.8+ requirement).
- **Python:** 3.14 (default), 3.12 (repo standard), 3.10 — via `py` launcher.
- **Docker Desktop:** installed, **not running**; backend = WSL2. Distros: `docker-desktop` (Stopped),
  `Ubuntu` (Stopped). Docker Desktop needs a logged-in user session — clashes with this box's
  headless boot-without-login NSSM design.
- **NGC API key:** none set; `~/.docker/config.json` auths empty.

## Key correction to the epic

The epic claims A2F needs **~0.6 GB VRAM** and "no unload/reload needed." **Both are wrong.**

- **NIM microservice:** ~**9 GB** VRAM non-optimized (`0.15·streams + 9`, FP16); 16 GB for the
  optimized RTX 5080 profile. Support matrix OS = Ubuntu 24.04 (Windows/WSL2 untested); listed
  GPUs are RTX **4090/5080/5090** — the **4070 is not listed**. Needs an NGC key + Docker.
- **Open-source SDK (local inference):** ~**4 GB+** VRAM recommended.

**Coexistence is mandatory, not optional:** A2F consumes TTS audio *live during speech*, and STT
must stay resident to detect barge-in *during* speech — so STT + TTS + A2F are all resident at
once. You cannot unload one to fit A2F.

| Resident set | VRAM | Fits 12 GB? |
|---|---|---|
| STT (~2.5) + TTS (~4.0) + **NIM A2F (~9)** | ~15.5 GB | ❌ No |
| STT (~2.5) + TTS (~4.0) + **SDK A2F (~4)** + Win overhead (~1–2) | ~11.5–12.5 GB | ⚠️ Borderline (4.8 GB free now) |

## Path comparison

### A. NIM (Docker + gRPC) — the epic's assumed path — **rejected**
- ~9 GB VRAM → does not coexist with STT+TTS on a 12 GB card.
- Ubuntu-only (Windows/WSL2 untested); 4070 not on the supported list.
- Requires an NGC account/API key (absent) and Docker Desktop running (needs a login session,
  breaking the headless NSSM model).

### B. Audio2Face-3D-SDK (native Windows) — **the only viable path, non-trivial**
- Repo: `github.com/NVIDIA/Audio2Face-3D-SDK`. C++/CUDA DLL + `run_sample.bat`; Windows supported.
- **Emotion input supported** (Audio2Emotion v2.2) → validates the "tag feeds A2F emotion" design.
- Footprint ~4 GB+ → borderline-fits alongside STT+TTS. Must measure.
- **Gates / costs:**
  1. **Build from source** — Visual Studio 2022+, `build.bat`. No prebuilt binaries/releases.
  2. Toolchain: **CUDA 12.8+ (<13.0)** and **TensorRT ≥10.13 (<11.0)** on PATH.
  3. Models are **HF-gated** — must accept NVIDIA licenses + `hf auth login` (needs an HF account).
  4. **No Python inference binding** — C++/DLL only; we wrap the DLL / `sample-a2f-executor.exe`
     in our own WS service to feed PCM and emit blendshapes.

## Verdict

The NIM is not viable on this box. The SDK path is viable but requires a real toolchain install
(VS2022 + CUDA 12.8 + TensorRT 10.13), HF license acceptance on the user's account, a from-source
build, and a wrapper service — and VRAM will be tight. The epic's VRAM budget and "lightweight,
no reload" framing must be revised. Decision on whether to invest in the SDK path is pending.

## Phase 0 infra brought up (2026-07-03) — GPU-in-docker WORKS

Chosen simple path (per user): run the A2F-3D **NIM container inside Ubuntu WSL2** headlessly (no
Docker Desktop — it needs a GUI session this box lacks). Getting GPU passthrough into native
dockerd in WSL took several fixes; the working recipe:

1. **WSL was the old inbox build** (`wsl --version` invalid) → no systemd. Fixed with
   `wsl --update --web-download` → Store WSL **2.7.10**, kernel 6.18.
2. **systemd**: `/etc/wsl.conf` → `[boot]\nsystemd=true`, then `wsl --shutdown`. PID1 is now systemd.
3. **docker**: `apt install docker.io nvidia-container-toolkit` in WSL; `systemctl enable --now docker`
   (persistent). dockerd bridge failed until iptables switched to legacy:
   `update-alternatives --set iptables /usr/sbin/iptables-legacy` (+ ip6tables).
4. **GPU passthrough**: hand-rolled CSV mode mounted nothing; the WSL-correct method is **CDI**:
   `nvidia-ctk cdi generate --mode=wsl --output=/etc/cdi/nvidia.yaml`, then run with
   `docker run --device nvidia.com/gpu=all ...` (docker 29 has native CDI; the nvidia *runtime* is
   not needed for this).

Verified: `docker run --rm --device nvidia.com/gpu=all nvidia/cuda:12.4.1-base-ubuntu22.04 nvidia-smi`
→ **RTX 4070, 12282 MiB, 4818 MiB free, driver 596.49** inside the container.

Persistent across reboots: systemd docker.service (enabled), iptables-legacy, `/etc/cdi/nvidia.yaml`.
**Caveat:** the CDI spec pins a driver-store path (`nvrfi.inf_amd64_*`); **regenerate the CDI spec
after any Windows GPU-driver update** (`nvidia-ctk cdi generate`).

**Remaining blocker:** an NGC API key (free NVIDIA account) to `docker login nvcr.io` and pull
`nvcr.io/nim/nvidia/audio2face-3d`. Then: pull with a light model profile, stop STT/TTS to free
VRAM (~9 GB NIM won't coexist), run the sample client, measure VRAM/FPS/emotion.

## Phase 0 RESULT (2026-07-04) — A2F-3D NIM ran end-to-end on the 4070 ✅

Pulled `nvcr.io/nim/nvidia/audio2face-3d:2.0.0` (26.4 GB, on E:) and ran it in Ubuntu WSL2 via
`docker run --device nvidia.com/gpu=all --network=host -e NGC_API_KEY=… -v cache:/tmp/a2x
-v hub:/opt/nim/.cache …` (both cache mounts must be **world-writable** — the NIM runs as a
non-root user; a root-only 700 dir crashes it with `PermissionError … /tmp/a2x/a2e.trt`).

- **GPU profile:** no 4070 profile exists → NIM falls back to the **rtx4090** profile, loading
  `james_v2.3.1_fp16_bs94` (A2F) + `a2e_v2.1_fp32_bs94` (emotion). Prebuilt `.trt` engines
  (downloaded, no local build). Uses the **James** model → client uses `config_james.yml`.
- **VRAM:** NIM alone = **~8.8 GB** (8896 MiB used vs 58 idle). Confirms the epic's 0.6 GB was
  wrong. With STT+TTS also loaded the card hit **11976 / 12282 MiB (97 %, 37 MiB free)** — it
  *technically* co-resided once but is far too fragile for always-on. **Coexistence not viable**
  as-is. (The bs94 profile is sized for 94 streams; a lighter model [claire/mark] or a
  fewer-stream profile may cut VRAM — untested follow-up.)
- **Output:** `animation_frames.csv` = full **ARKit blendshape set** (`EyeBlink*`, `JawOpen`,
  `MouthSmile/Frown/Funnel/Pucker`, `BrowDown/InnerUp/OuterUp`, `CheekPuff/Squint`, `NoseSneer`,
  `Tongue*` — 68 shape columns). **~30 FPS** (381 frames / 12.68 s audio), processed in ~5.6 s
  wall (**~2.3× faster than realtime**).
- **Emotion:** confirmed both directions — `a2f_3d_input_emotions.csv` (specified) and
  `a2f_3d_smoothed_emotion_output.csv` (A2E-detected: grief/joy/anger/sadness/fear/…). Validates
  decisions #5/#6 (emotion tag → A2F emotion input).

**Verdict:** A2F-3D works and emits exactly the blendshapes+emotion Epic 8 needs. The blocker for
*always-on* deployment on this box is VRAM: the NIM (~9 GB) cannot safely coexist with STT+TTS on
one 12 GB card. Next decision: lighter NIM profile (claire/mark, fewer streams) vs the leaner
SDK path vs a dedicated GPU. The NIM path itself is proven.

## VRAM deep-dive: why the NIM needs ~8.8 GB, and why it can't be tuned down (2026-07-04)

The NIM footprint is **not the model** — james_v2.3.1 is a lightweight *regression* model (weights =
hundreds of MB). The memory is the **TensorRT engine's activation buffers, and the shipped engine is
built for batch-94** (`james_v2.3.1_rtx4090_fp16_bs94`). A neural net at batch N holds N copies of
every intermediate tensor at once; the engine preallocates that at load time for the max batch. The
NIM is a datacenter product — bs94 lets one GPU serve ~94 avatars for throughput/cost (the support
matrix's `0.15·streams + 9` formula is literally a per-stream scaling model). We run **1** stream on
a consumer 12 GB card, so we inherit ~9 GB of cloud-scale overhead we don't use.

**Tested `PERF_MAX_STREAM=1`** (2026-07-04): log confirmed `Successfully updated stream_number to 1`,
but VRAM only moved **8896 → 8680 MiB**. Runtime stream limiting does not shrink an *already-built*
bs94 engine — the memory plan is baked at build time. The 4070 also has no smaller profile (only the
rtx4090 bs94 fallback). **Conclusion: the NIM is effectively pinned at ~8.6–8.8 GB on this box** and
cannot coexist with STT+TTS. To get a small engine you must **rebuild it at batch=1**, which the NIM
cannot do (it only ships prebuilt engines) — but the **open-source SDK can**.

## Pivot to the Audio2Face-3D-SDK (rebuild a batch-1 engine)

Repo: `github.com/NVIDIA/Audio2Face-3D-SDK` (C++/CUDA, cross-platform, Linux build scripts present).

**Recon — the batch lever (the whole reason this works):** the SDK's ONNX→TRT conversion
(`audio2x-common/scripts/audio2x/trt.py :: convert_onnx_to_trt`) builds via `trtexec` with dynamic
shapes on tensor `input_values`: **min `1×5000` / opt `1×30000` / max `1×60000`**. The **first
(batch) dim is 1** — the variable dim is *audio length*, not tracks. So the SDK **builds a
single-stream (bs1) engine by default**. Expected footprint ≈ weights + 1-wide activations + fixed
CUDA/cuDNN/TRT context + a2e model ≈ **~2–4 GB** → fits alongside STT+TTS (~2.5+4+~3 ≈ 9.5 GB).

**Build plan (inside a container, using our working docker+GPU):**
- Toolchain: **`nvcr.io/nvidia/tensorrt:25.08-py3`** = TensorRT **10.13.2.2** + CUDA **12.9** (matches
  SDK reqs: CUDA ≥12.8<13, TRT ≥10.13<11) — ships `nvcc` + `trtexec` + TRT dev libs. Pulled via our
  nvcr.io login. Run with `--device nvidia.com/gpu=all`.
- Steps (Linux): `git clone` + `git lfs pull` → `./fetch_deps.sh release` (packman pulls cmake/ninja)
  → `export TENSORRT_ROOT_DIR=…` → `./build.sh all release` → `pip install -r deps/requirements.txt`
  (needs python 3.8–3.10) → `hf auth login` → `./download_models.sh` → `./gen_testdata.sh` (**builds
  the bs1 TRT engine**) → `./run_sample.sh` → measure VRAM.
- **Gates:** models are **HF-gated** — need a HF account, license acceptance on
  `nvidia/Audio2Face-3D-*` + `nvidia/Audio2Emotion-v2.2`, and a HF read token (like the NGC gate).

**Status:** container pulling; awaiting HF token to download models. Build results below (TBD).

### SDK build results (2026-07-04)

Built inside `nvcr.io/nvidia/tensorrt:25.08-py3` (mounting the host clone + a persisted packman cache),
`--device nvidia.com/gpu=all`. Findings:

- **CUDA 13 is fine** despite the README's "<13.0": CMake only enforces `minimum required 12.8` —
  `Found CUDAToolkit "13.0.48"` accepted, TensorRT 10.13.2 found, all packman target-deps resolved.
- **One real fix needed:** container ships zlib **1.3**, SDK requires **≥1.3.1**. Build zlib 1.3.1 to
  `/usr/local` and pass `ZLIB_ROOT=/usr/local CMAKE_PREFIX_PATH=/usr/local`.
- **Packman gotcha:** `_deps/build-deps/{cmake,ninja}` are symlinks into `/root/.cache/packman`
  (ephemeral in a `--rm` container) — run `fetch_deps` + `build` in the **same** container invocation,
  and mount the packman cache to a host dir to persist it.
- **Build succeeded:** `build rc=0`, 147/147 targets. Artifacts in `_build/release/`:
  `audio2x-sdk/lib/libaudio2x.so`, `audio2face-sdk/bin/{sample-a2f-executor, sample-a2f-a2e-executor,
  sample-a2f-low-level-api-fullface}`, `audio2emotion-sdk/bin/sample-a2e-executor`.

**Remaining (needs HF token + license accept):** `pip install -r deps/requirements.txt` → `hf auth login`
→ `download_models.sh` (James + a2e) → `gen_testdata.sh` (**builds the bs1 TRT engine**) →
`run_sample.sh` → measure VRAM at bs1. Results below (TBD).
